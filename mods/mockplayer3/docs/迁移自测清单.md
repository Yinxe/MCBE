# 游戏内自测清单（迁移后验收）

> 对应 `openspec/changes/migrate-mockplayer3/tasks.md` 的 7.3 / 7.4 / 7.5。
> 这三条是**只有真人进游戏才能做**的验收，本仓库环境无 Minecraft 客户端，故单列此清单交付。

## 为什么必须实测

本次迁移有一处**代码被重写**：`scripts/interface/CmdKit.ts` 的 `defineCommand`。上游把它委托给 `@yinxe/toolkit`，而 `@mc-toolchain/mod-common` 刻意不提供命令注册封装，因此按上游语义就地实现了一份。

它的关键职责是**把处理器推迟到安全上下文**（上游用 `runSafeAsync`，本实现用 `runSafeDetached`）。自定义命令回调与 `beforeEvents` 回调都运行在**只读上下文**，在其中调用被标注 `can't be called in read-only mode` 的成员会抛错。

若这层推迟漏掉或失效，症状不是报错，而是**「命令返回成功但什么都没发生」**——玩家看到命令被接受，世界毫无变化，日志也没有异常。这类缺陷 `tsc` 与单测都抓不到（单测只能证明「回调返回时处理器尚未执行」，不能证明「flush 之后游戏 API 真的可用」），只有进游戏才看得见。

`tests/interface.CmdKit.test.ts` 已用 7 条用例覆盖注册链路的四项语义（非玩家拒绝、参数归一、枚举先于注册、推迟时序）。**本清单是它的游戏内补充，不是替代。**

## 前置准备

| 项 | 要求 | 不满足的症状 |
| --- | --- | --- |
| 游戏版本 | **1.26.10 或更高** | 低于此版本时 `world.tickingAreaManager` 为 `undefined`，常加载相关代码运行时抛错（见 `design.md` R1：清单声明 `[1,21,130]`，但实际 API 地板是 1.26.10，此为上游既有不一致，本次未改） |
| 世界实验开关 | 开启 **Beta APIs** | 模组清单声明 `@minecraft/server` = `"beta"`，未开时**整个脚本不加载**，且无任何错误提示——表现为「装了但什么都没发生」 |
| 测试世界 | 建议新建，不要用正式存档 | 7.4 需要「用上游版本存档替换」的对比测试 |
| 操作身份 | 需 OP（管理员） | `mp:admin` 等命令要求管理员权限 |

安装包：`release/mockplayer3-v3.0.32.mcaddon`（同时含行为包与资源包）。

## 判读通则

每条用例都看**两件事**，缺一即判失败：

1. **聊天栏反馈**——每条命令都有明确文案（成功文案含 `color.success`，失败含 `color.error` 前缀）。
2. **世界状态真的变了**——不能只看反馈。例如 `mp:create` 必须肉眼看到世界里多出一个假人实体；`mp:online` 必须看到假人从静止变为可交互。

**出现「有反馈但世界没变」= 推迟语义失效 = 必须回报，不要继续后续用例。**

## 7.3 命令生效（验证推迟语义）

按 design R3 的验收口径，覆盖生命周期、导航、行为、物品、面板五类。**按顺序执行**，前一条是后一条的前提。

### ① 生命周期：`mp:create`

```
/mp:create 测试1
```

- **预期反馈**：创建成功提示，含假人名「测试1」。
- **预期世界变化**：世界中**出现**一个名为「测试1」的假人实体，站在你附近。用 `/mp:listbots` 可列出它。
- **失败特征**：提示成功但世界里找不到实体 → 推迟失效。
- **记录**：反馈文案原文 = ______ ；实体是否可见 = ______

### ② 生命周期：`mp:online`

```
/mp:online 测试1
```

- **预期反馈**：上线成功提示。
- **预期世界变化**：假人**上线**（可被攻击、可交互、会响应工作模式）。同时用 `/tickingarea list` 应能看到 `mpa:` 前缀的区域。
- **失败特征**：提示上线但假人仍是「离线」状态（无碰撞、不响应命令）。
- **记录**：反馈 = ______ ；`tickingarea list` 中 `mpa:` 条目 = ______

### ③ 行为：`mp:work` 切模式

```
/mp:work 测试1 跟随
```

（`跟随` 是 `domain/Catalog.ts` 的 `WORK_MODES` 表中 `follow` 条目的 label；也可用 id `follow`。无参执行 `mp:work 测试1` 会列出全部模式与当前值。）

- **预期反馈**：模式切换成功，显示新模式「跟随」。
- **预期世界变化**：**假人开始跟着你走**——你走开它会追上来（距离带 3~128 格）。这是最容易肉眼确认的一条。
- **失败特征**：提示已切到「跟随」但假人原地不动 → 推迟失效或调度未启动。
- **记录**：反馈 = ______ ；假人是否跟随 = ______

### ④ 导航：`mp:tphere`

```
/mp:tphere 测试1
```

- **预期反馈**：传送成功提示。
- **预期世界变化**：假人**立刻出现在你身边**（不是走过去，是瞬移）。
- **失败特征**：提示成功但假人还在原地。
- **记录**：反馈 = ______ ；假人位置是否改变 = ______

### ⑤ 面板：`mp:menu`

```
/mp:menu
```

- **预期反馈**：无聊天反馈，直接**弹出表单界面**。
- **预期世界变化**：出现模拟玩家管理菜单，能看到「测试1」条目；点进去能看到操作面板。
- **失败特征**：命令被接受但界面不弹（这是表单调用在只读上下文失败的典型表现）。
- **记录**：界面是否弹出 = ______ ；能否看到「测试1」= ______

### ⑥ 物品：`mp:reclaim`

```
/mp:reclaim 测试1
```

- **预期反馈**：成功时形如 `已从 <假人名> 回收: N 件物品、M XP（Lv.K）`；若假人背包为空则回 `假人 <名> 背包是空的`。失败时回 `回收失败: <原因>`。
- **预期世界变化**：假人背包里的物品与经验**转移到你身上**。建议先给假人塞点东西（`mp:menu` 面板或直接丢给它）再测，否则只会得到「背包是空的」，无法证明转移真的发生。
- **失败特征**：提示回收成功但你的背包没变化。
- **记录**：反馈 = ______ ；你的背包/经验是否增加 = ______

### 7.3 判定

六条全部满足「有正确反馈 **且** 世界状态真的改变」→ 7.3 通过。

任何一条出现「有反馈但世界没变」→ **停止测试，回报该条命令与现象**。这指向 `CmdKit.ts` 的推迟语义，属于本次迁移的高风险项，需要修代码而非重测。

## 7.4 面板与存档兼容

### ① 全局配置面板

```
/mp:admin
```

- 打开管理员菜单（默认配额 / 逐玩家配额 / 管理员名单三块）。
- **改动一项**（例如把默认配额改一个值）→ 关闭面板 → **退出世界再重进** → 重新 `/mp:admin`。
- **预期**：改动**仍在**。
- **记录**：改了哪项 = ______ ；重进后是否保留 = ______

### ② 假人操作面板

```
/mp:menu  →  选中「测试1」
```

- 打开该假人的操作面板，**改动一项**（例如工作模式、或某个开关）→ 退出重进 → 复查。
- **预期**：改动保留。
- **记录**：改了哪项 = ______ ；重进后是否保留 = ______

### ③ 长流程脚本面板

```
/mp:flow 测试1
```

（`mp:flow` 是长流程模式：添加/查看/清空/循环/运行/停止/状态/导出。）

- 添加一条指令表条目 → 退出重进 → 用 `/mp:flow 测试1` 查看。
- **预期**：条目仍在。
- **记录**：添加了什么 = ______ ；重进后是否保留 = ______

### ④ 旧存档兼容（关键）

这一步验证**迁移没有破坏已有玩家的存档**。

1. 用**上游版本**（`~/coding/MCBE/mcaddon/` 里那份 v3.0.32 原版）创建一个世界，建几个假人、各设不同工作模式、往物品仓存点东西、改几项全局配置，然后**保存退出**。
2. 把该世界的行为包/资源包**替换**为本次迁移的产物（UUID 未变，游戏应识别为同一个包，直接覆盖即可）。
3. 进入世界，逐一核对：
   - 假人**列表完整**（`/mp:listbots`）——名字、数量都对。
   - 每个假人的**工作模式**与原来一致（`/mp:work <名>` 查看）。
   - **物品仓内容**在（`/mp:storage <名>` 可看 NBT 存储绑定与实存物品）。
   - **全局配置**在（`/mp:admin`）。
   - 假人能**正常上线**并按**原工作模式**运行（`/mp:online <名>`，观察行为是否符合该模式）。

- **记录**：假人数 = ______ ；模式是否一致 = ______ ；物品仓是否完整 = ______ ；能否上线并运行 = ______

> 这一步是本次迁移**最重要的验收**。UUID 与版本号全部保持原值正是为了它——若这里失败，说明数据格式在迁移中被改动，需立刻回报。

## 7.5 常加载与物品仓

### ① 常加载区域的申请与释放

```
/mp:online 测试1
/tickingarea list
```

- **预期**：列表中出现 **`mpa:` 前缀**的区域。命名规则（`scripts/engine/TickingAreas.ts:1-22`）：
  - `mpa:aux:shared` — 上线辅助，全局共享、用完即释、永不独占
  - `mpa:<botId>:sc` — 单区块档，下线保活
  - `mpa:<botId>:wa` — 工作档，作业中的漫游保活
  - `mpm:` — **管理员手工**区域前缀（`/mp:chunkarea add` 创建），属持久意图，不参与孤儿清扫，故不应被自动释放

  键含 `botId` 不含显示名，所以不要按假人名去找区域。
- 然后 `/mp:offline 测试1` → 再 `/tickingarea list`。
- **预期**：相应区域**被释放**（`mpa:<botId>:wa` 应消失；`sc` 保活档可能留存，符合设计）。
- **记录**：上线后出现的区域名 = ______ ；下线后是否释放 = ______

### ② 物品仓 NBT 保真（关键）

这一步验证**带 NBT 的物品往返后不丢数据**——这是物品仓最容易出问题的地方。

1. 准备一件**带附魔 + 自定义名称 + 有损耗耐久**的物品（例如附魔金镐，改名「测试镐」，用掉一点耐久）。
2. 通过面板或 `mp:storage` 相关操作把它**存入**假人物品仓。
3. 让假人下线（`/mp:offline 测试1`）→ 再上线（`/mp:online 测试1`）。
4. 把物品**取出**。
5. 逐项核对：
   - **附魔**是否还在（等级也对）
   - **自定义名称**是否还是「测试镐」
   - **耐久**是否与存入时一致（没被重置为满耐久，也没丢损耗）

- **记录**：附魔 = ______ ；名称 = ______ ；耐久 = ______

> 若 NBT 丢失，指向 `packages/nbt-data-storage` 的迁移。该包 110 条单测全绿，但单测用的是构造的 NBT 快照，真实引擎序列化路径只有游戏内能验。

## 回报模板

把上面每条的「记录」填好即可。若有失败项，附上：

- 命令原文
- 聊天栏反馈原文（截图或复制）
- 实际世界状态 vs 预期
- 若内容相关的日志报错，贴出原文

**最需要盯的两处**：7.3 的「有反馈但世界没变」（推迟语义），7.4-④ 的旧存档兼容（数据格式）。这两处任一失败都说明迁移引入了真实缺陷。
